# Streams and video info

## Why NewPipeExtractor

The same reasons as YouPipe Music (see its `docs/streaming.md`): InnerTube `/player` URLs stop at about 1 MB without a PO token, and NewPipeExtractor works around that. **When playback breaks, bump `com.github.TeamNewPipe:NewPipeExtractor:<tag>` in `android/app/build.gradle.kts` first.** It needs `coreLibraryDesugaring` and the R8 keep rules in `proguard-rules.pro`.

## `getVideoInfo({videoId, hl, gl, maxHeight})`

One extraction per video, run on a 3-thread executor in `StreamExtractorChannel.kt`. It returns:

| Key | What |
|---|---|
| `title`, `channelId`, `channelName`, `channelAvatar`, `channelVerified`, `subscriberCount`, `viewCount`, `likeCount`, `uploadDate`, `description` (HTML), `ageLimit`, `isShort` | Metadata. **Best-effort:** each getter is wrapped, because a NewPipe getter that trips on a changed response (a Short failed this way in Phase 0) mustn't block playback |
| `durationSeconds`, `isLive` | |
| `dashMpd`, `dashHeights`, `dashCodec` | A static DASH manifest (see below), or null |
| `muxedUrl`, `muxedHeight` | YouTube's progressive stream with audio and video in one file (360p) |
| `hlsUrl` | Live streams |
| `dashUserAgent`, `muxedUserAgent`, `hlsUserAgent` | **One per source**; see below |
| `captions` | `[{url (VTT), languageCode, name, autoGenerated}]` |
| `storyboards` | `[{urls, frameWidth, frameHeight, totalCount, durationPerFrameMs, framesPerPageX, framesPerPageY}]` (usually 2 levels) |
| `chapters` | `[{title, startSeconds, thumbnail}]` |
| `audio` | Progressive audio streams (original track, DRC copies dropped), for a later audio-only mode |

### The DASH manifest

- **Contents:** one `AdaptationSet` of video-only Representations (one per height, 144p up to `maxHeight`) plus the best audio stream (Opus preferred). Each Representation carries its `BaseURL` and `SegmentBase` byte ranges, the same builder as YouPipe Music.
- **One codec family per manifest,** so ExoPlayer can switch heights:
  - **H.264** by default (YouTube offers it up to 1080p).
  - **VP9** when more than 1080p is wanted, VP9 goes higher than H.264, and `MediaCodecList` reports a **hardware** VP9 decoder.
- **Where it plays:** `VideoInfoService` writes the manifest to `<temp>/video/<id>_<maxHeight>.mpd`, which plays with `formatHint: VideoFormat.dash`.
- **ExoPlayer caps the chosen height to the display size,** so on the 1080p test phone a 4K manifest plays at 1080p–1440p.

## Stream URLs are bound to their client

- A googlevideo URL carries `c=` (the InnerTube client that produced it) and `ip=`. It only plays from this phone, with that client's User-Agent (`Googlevideo.userAgentFor`).
- **NewPipe mixes clients.** In every Phase 0 extraction (v0.26.5):
  - the **DASH** video and audio streams came from `VISIONOS`;
  - the **muxed** stream came from `ANDROID`.

  Sending the ANDROID User-Agent with the manifest caused intermittent 403s, so each source now has its own User-Agent.
- **Even with the right User-Agent, a VISIONOS DASH request occasionally gets a 403.** In Phase 0 that happened once in about 25 videos, and it didn't repeat for the same video.
  - **Mitigation:** `VideoPlayerService` re-resolves once (`forceRefresh`) and resumes at the same position.
  - **Root cause not known yet.** If this happens more often, the next step is a local relay that fetches in 1 MB ranges, like YouPipe Music's `CastProxy.kt`.

## Caching and retries (`VideoInfoService`)

- Results are cached per `videoId@maxHeight` until 10 minutes before the URLs' `expire`. Concurrent requests for the same key share one future.
- **`EXTRACTION_FAILED` is retried once after 1 s.** YouTube sometimes answers NewPipe's `visitor_id` call with an HTML page.
- **Pitfall:** in `whenComplete`, never return the future you're removing from `_pending`. `whenComplete` waits on whatever its callback returns, so the future would wait on itself forever. This happened in Phase 0.

## The bot check and the address family (`Googlevideo.kt`)

- **What it is:** after heavy use, YouTube answers the ANDROID player request with `LOGIN_REQUIRED` "Sign in to confirm that you're not a bot". It's the only client NewPipe validates, and it runs first, so the whole extraction fails (iOS and VisionOS are never tried).
- **It's per address, and per address family.** On 2026-10-03 the phone (dual-stack, IPv6 preferred) was blocked over IPv6 while the PC on the same network, over IPv4, got `OK` from ANDROID, iOS and VisionOS. Signing in doesn't help: NewPipe's mobile clients can't carry a web session.
- **The fallback (`StreamExtractorChannel.fetchExtractor`):** on a bot check, `Googlevideo.switchFamily()` flips the shared OkHttp client's DNS order (IPv4 first, or the system's order), evicts pooled connections, and retries once. The choice is remembered in the native `youpipe_network` preferences (`preferIpv4`) and loaded by `Googlevideo.attach` in the activity and the download worker. It flips again at the next bot check, so a flag on either family is routed around (on mobile data the shared IPv4 is often the flagged one).
- **Everything native shares that client:** NewPipe's downloader, downloads and the cast proxy. ExoPlayer still connects in the system's order; googlevideo played IPv4-resolved URLs fetched over IPv6 without a 403 (checked 2026-10-03).
- **Not the fix:** a `PoTokenProvider`. In v0.26.5 only the ANDROID and iOS requests take PO tokens, and those need device attestation; a web BotGuard token doesn't apply.
- **When both families are flagged,** the player shows `BOT_CHECK` ("YouTube wants to confirm you're not a bot. Try again in a while").

## Downloads and casting

- **Download options:** `getVideoInfo` returns `downloadOptions`, one `{height, size}` per H.264 height (video + best AAC), plus the muxed stream. `DownloadWorker.kt` resolves its own fresh streams (docs/downloads.md).
- **Casting:** `castStream(videoId)` gives the muxed progressive stream for `CastProxy.kt` (docs/cast.md).
- **Downloads play offline:** the player checks `VideoPlayerService.localVideo` before any extraction.

## Throttling note (from YouPipe Music, 2026-10-03)

- **The problem:** googlevideo throttles ExoPlayer's open-ended range requests to about 2× real time. YouPipe Music fixed buffering with a loopback relay (`PlaybackProxy.kt`) that fetches 1 MB ranges.
- **Where YouPipe is affected:**
  - DASH playback here requests bounded segment ranges (from the `SegmentBase` index), so it's mostly unaffected.
  - The muxed 360p fallback and Shorts without a manifest are affected.
- **The relay (`PlaybackProxy.kt`, `lib/player/playback_proxy.dart`):** adapted from YouPipe Music. The muxed stream (in the player and in Shorts without a manifest) plays from `http://127.0.0.1:<port>/s/<token>`; the relay fetches googlevideo in 1 MB ranges with the client's User-Agent through `Googlevideo.client`, so it also follows the address family extraction used. Upstream errors pass through as HTTP codes, so the player's 403 recovery still runs. If the relay can't start, the stream plays directly.
- **DASH isn't relayed:** its segment requests are already bounded ranges.
- **Plain HTTP to 127.0.0.1 is allowed only there:** `res/xml/network_security_config.xml` permits cleartext for that one host, which ExoPlayer needs to reach the relay (without it: "Source error"). Everything else stays HTTPS-only.
- **Testing it:** the relay only runs when DASH fails, so build with `--dart-define=FORCE_MUXED=true` to skip the manifest (checked 2026-10-04: a 2-hour video played muxed through the relay).

## Player (`lib/player/video_player_service.dart`)

- **Source order:**
  1. live → HLS;
  2. otherwise the DASH manifest;
  3. muxed 360p if the manifest fails to initialise.

  `initialize()` times out after 20 s.
- **Background and notification:** `VideoPlayerOptions(allowBackgroundPlayback: true)` keeps the video playing in the background. `YouPipeAudioHandler` mirrors it to the media session (notification, lock screen, headset), which keeps the process in the foreground.
- **PiP:** `Pip.arm(true, aspect)` while the watch page has a video. Android 12+ then enters PiP automatically on Home (`setAutoEnterEnabled`); older versions enter from `onUserLeaveHint`. The watch page shows only the video while `Pip.active` is set.
